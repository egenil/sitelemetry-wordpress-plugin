# Changelog

## 0.1.3 - unreleased

- Passing checks: the checks with status `ok` from `auditDetails.checks.items` (and, for a full audit, `auditDetails.pillars[*].checks.items`) and the service's `passingFindings` are stored with the result (at most 300 items and 40,000 characters; titles 180 and evidence 300 characters) and listed in a collapsible "Passing checks (N)" section grouped by security module. A full audit, which sends no `passingChecks`, gets its count from the list. Results stored by 0.1.2 show the count and a note that the list appears after the next audit.
- What was not measured: a collapsible section with readable module names and the explanations the browser extension gives (redirects, 429, 5xx, no answer in time, silently dropped ports, the per-audit script limit), the service's reason underneath, and a link to the verification helper for modules that need verification.
- Copy AI fix prompt on completed and partial results: a PHP port of the extension's prompt builder (neutralized service text, BEGIN/END data fences, no API key or job ids, 30,000-character cap, truthful notes, answer in the admin's WordPress language), copied with `navigator.clipboard` and a read-only textarea fallback.
- Verify this site: paste the token from the app and the plugin answers `/.well-known/sitelemetry-verification.txt` on this site's host (200 `text/plain`, `no-store`, token only; 404 without a token), served on `parse_request`. "Test the file" reports the exact problem. The results page and the dashboard widget show a verification call to action with the 30-day renewal reminder. DNS TXT and Search Console are documented as alternatives.
- One-click verification through the service's verification API (`GET /api/v1/verification/status`, `POST /api/v1/verification/challenge`, `POST /api/v1/verification/verify`, the same MCP API key as a Bearer token, server to server with the WordPress HTTP API): "Verify this site" asks for the status (a fresh verification ends there with "Verification complete ✓ valid until <date>"), requests the challenge, publishes the token only when the challenge URL is exactly this site's host and verification path, runs the self-test and asks Sitelemetry to verify. Failures are stored as the service's lower_snake code and reason and explained with the fix in the viewer's language (404 from a server that keeps `/.well-known/`, 401/403, other statuses, redirects such as www versus non-www, body mismatch, timeout, no public address, DNS, TLS, body over 2 KB, connection, changed challenge, rate limit with the wait, verification in progress, invalid or revoked key, invalid target, pending limit, verifier unavailable, network errors). DNS TXT and Search Console stay documented as alternatives. After a success the calls to action of earlier results say the site is verified and ask to run the audit again. `Sitelemetry_Audit_Verification_Api` takes an injectable HTTP layer; the placeholder `one_click_available()`/`request_one_click()` are now the real implementation.
- The Verify button is shown disabled with a hint until an API key is saved. With a key, one read-only status request detects the API (cached per key: 7 days when present, 1 hour when the service answers like an unknown path, 5 minutes when unreachable). When the API is off or not deployed, the button is hidden, a neutral note is shown and the manual token helper stays exactly as before; with the API on, the manual steps stay available in a collapsed section.
- Automatic renewal in WP-Cron (`sitelemetry_audit_verification_renew`): at expiry, when an audit of this site reports `target_reverification_required`, when the status probe reports `stale`, at the expiry of a valid verification the status probe finds without a scheduled renewal (made in the app, or before the API key changed), and before the weekly audit when the verification is known to have expired. It renews only what the service reports as stale (a fresh verification is never sent to `challenge`; when this server's clock is already past the expiry but the service still reports the verification as fresh, the next attempt waits 15 minutes instead of running on every WP-Cron call), retries failures (15 minutes for passing problems, 6 hours otherwise, at most 5 in a row) and shows an admin notice on the Dashboard and Plugins screens only when the renewal fails. On multisite it runs only where a network administrator stored the token; filter `sitelemetry_audit_auto_renew`. Changing the API key drops what the plugin knew about the old account's verification.
- Onboarding on the settings page: one button, "Sign in or create an account" (`https://sitelemetry.com/app?utm_source=wordpress-plugin&utm_medium=plugin`, the plugin's UTM parameters and no plan parameter: the app opens its sign-in screen, and new users switch to its "Create account" tab, the ordinary sign-up with the plan choice and payment), and a "Get your API key" link (`https://sitelemetry.com/app?view=account&utm_source=wordpress-plugin&utm_medium=plugin`, the view with the MCP API key, opened after sign-in), both in a new tab. `/app?plan=free` is not used: the app treats exactly that URL as the neutral free-only entry of the AI-directory (MCP/OAuth) sign-ups. The key instructions name the app's "My account" and "Manual connection and API key"; the readme says that Sitelemetry has free and paid plans.
- 47 new strings, translated in all nine locales (335 per catalogue); `tests/test-one-click.php` covers every path against an in-process stand-in of the API, and `tests/test-i18n.php` checks that the onboarding button uses the app's own "Sign in" and "Create account" terms in every locale.
- The first `tools/call` sends `lang` from the admin's locale (en, tr, es, de, fr, pt, it, ja, zh; otherwise en); polls re-send `pollArguments` unchanged.
- Removed the "Open the full report" button, the remaining-scans lines and every sentence that promised a report or result in the app: the general `/mcp` endpoint returns neither, and Sitelemetry keeps no report of these audits.
- Test fixtures follow the service's real result shape (check statuses `ok`, `observed`, `fail`, `skipped`, `error`, `not_applicable`, `manual_review`; `auditDetails.checks.items`; no `reportUrl`).
- Translations: complete `.po`/`.mo` files for tr_TR, es_ES, de_DE (du), de_DE_formal (Sie), fr_FR, pt_BR, it_IT, ja and zh_CN, with the terms of sitelemetry.com, the app's Verified Domains screen and the browser extension. The plugin still does not call `load_plugin_textdomain()` (Plugin Check discourages it on WordPress.org): WordPress.org language packs load just in time, and `Sitelemetry_Audit_I18n` offers the bundled `.mo` through `lang_dir_for_domain` (WordPress 6.6+) only when no language pack is installed. `docs/TRANSLATIONS.md` explains the import into translate.wordpress.org.
- The `.pot` includes the plugin header fields; the plan names in the fallback plan labels use the context "plan name" (`_x()`), so the price label "Free" can be translated while the plan name stays "Free".
- `tools/make-mo.mjs`: merges the template into every `.po` (`--sync`), fails on changed printf placeholders or wrong plural forms, compiles the `.mo` files and reads them back. `tests/test-i18n.php` checks the shipped catalogues and the fallback filter.
- Verification steps name the buttons of the Sitelemetry app exactly: Verified Domains, Start verification, HTTP verification file, Verify HTTP, Verify DNS and Reverify.
- Review fixes before release:
  - Multisite: publishing, testing and removing the verification file need `manage_network_options` (filter `sitelemetry_audit_verification_capability`); a site administrator sees why and gets the app link instead. A stored token is served on a network only when a user with that capability saved it. The server behind a site's host is shared by the network, so a published token must not come from one site's administrator.
  - AI fix prompt: the fallback without the intl extension maps every code point whose NFKC form contains a delimiter (U+2A74-2A76 and U+FE33/FE34 were missing, so "⩶ END AUDIT FINDINGS ⩶" passed unchanged); each finding is neutralized once and only the findings that can fit are prepared, so 2,000 long findings take under a second instead of about 15 seconds in php-wasm, with byte-identical output.
  - What was not measured on SEO, AI visibility and performance results: a partial result now lists what the service reports as unmeasured instead of "this result does not say which": the pages a crawl found but could not assess (named as disallowed by robots.txt when each of them is), an audit without any measurement ("Performance: unavailable (no measurement for this target)") and the metrics reported as unavailable ("Metrics not measured: LCP, INP, CLS, FCP, TTFB"); the pillars of a full audit are named. The AI fix prompt lists the same lines. 3 new strings, translated in all nine locales (338 per catalogue); `tests/test-outcome.php` uses real general `/mcp` results of sitelemetry.com (`seo-partial-robots.json`, `performance-unavailable.json`).
  - Checks with status `error`, `skipped`, `manual_review` or `not_applicable` are stored (at most 200) and listed under "What was not measured", grouped by status with a short explanation; the section also appears on completed results that have such checks, and the prompt counts them.
  - The running-audit status line is the plugin's own ("Sitelemetry is running the audit…"); the service's polling instructions for MCP clients are no longer shown.
  - After a weekly audit that needs verification or its renewal, a notice on the Dashboard and Plugins screens, dismissible per result.
  - WordPress 6.0 to 6.5: the bundled translation is loaded with `load_textdomain()` on `init` when no language pack is installed, so the screens match the language of the audit text.
  - Renewal: the results page no longer says the (used-up) token is already published; it asks for the new token.
  - "Test the file" results are stored as a code and written in the viewer's language; `HTTPS://` in a redirect is no longer reported as a downgrade; the token pattern rejects a trailing newline.
  - A rejected token is reported next to the token field; a non-default port gets a warning and "Open the file" keeps the port; IP and single-label hosts get no www or DNS record name.
  - Plugin Check: the `DONOTCACHEPAGE` line carries a justified `phpcs:ignore` (it is the page-cache plugins' constant).
  - "Remove token" also stops the automatic renewal: the scheduled event is cleared and no trigger (expiry, an audit reporting the expiry, the settings page probe, the weekly audit, activation) publishes a new token or verifies the host again until the admin clicks Verify this site or saves a token. Before, WP-Cron published a new token at the next expiry and Sitelemetry's host-level probes resumed with no admin action. The panel, the results call to action and the widget no longer promise an automatic renewal then.
  - Activation schedules the renewal also for a verification that expired while the plugin was inactive, a stale one and an unfinished renewal with retries left (before, nothing was scheduled while the panel said the plugin renews it).
  - The file test that runs inside one click or a renewal is no longer shown as a second, contradicting notice when it fails (for example "upload a plain text file with the token", which breaks the next renewal); the attempt's own reason explains it.
  - An audit of this site that reports `target_verification_required` or `verification_scope_required` ends "Verification complete" in the panel; the next settings page load asks the service once.
  - Texts: the failed-renewal notice no longer says "as described below" on the Dashboard; `not_public` gives a fix; the generic failure shows "HTTP" only before a status code; de_DE and de_DE_formal "Eigentum an der Website verifizieren".
  - Dashboard widget: the ": " and "( )" around the status and date come from translatable strings. Translations: es/pt audit-kind sentences, shorter API key placeholders (de, fr, es, it, ja), tr "alan adı düzeyindeki", de "Bereich" and zh "领域" for pillar, ja 検証 and spacing, es and tr wording, fr/pt "Check now" as a refresh; step 2 names the app's "verification code".

## 0.1.0 - 2026-09-21

First release.

- Settings > Sitelemetry: MCP API key (stored in the options table, shown masked, removable), target (defaults to the site address), audit kind (security by default; other kinds labelled with the plan they require, read from the public plan catalogue) and the optional weekly schedule.
- Manual audits through admin-post with nonce and capability checks. The MCP JSON-RPC contract (initialize, then tools/call audit_<kind>) is spoken with the WordPress HTTP API; no bundled libraries.
- Polling: while the results page is open, an admin AJAX loop asks WordPress for one step at a time; each step re-sends the server's pollArguments unchanged, inside the MCP session negotiated once per audit, and waits the full retryAfterMs the service asked for. A WP-Cron single event finishes a job whose browser tab was closed, and drives the weekly audit. A 20-minute time budget (filter `sitelemetry_audit_time_budget`) bounds every job.
- Results page: status banner (completed, partial with "What was not measured", plan_required, quota_exhausted, verification_required, blocked), score and grade, findings table with a severity filter, timestamps, coverage notes, the next step in the app, and a factual "Plan and usage" box (pricing link with `utm_source=wordpress-plugin&utm_medium=plugin`, link to ownership verification).
- Dashboard widget: last score, findings by severity, remaining scans when known, one button to the results.
- Last result per audit kind stored in one option (no personal data); uninstall removes options, transients and cron events.
- All strings translatable (text domain `sitelemetry-audit`, `languages/sitelemetry-audit.pot`).
